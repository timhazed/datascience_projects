# Evaluation

*This document reflects current thinking on how to measure AI system behavior under production conditions. Evaluation strategy is one of the most rapidly evolving areas of AI engineering — this document is updated as better methods emerge.*

---

## Purpose

Evaluation is the phase where a deployed or near-deployed system is measured against its stated success criteria under realistic conditions. It answers the question that review cannot: does the system do what it claims to do, at scale, on real inputs?

In traditional software, a passing test suite is strong evidence that the system works. In AI systems, it is necessary but not sufficient. LLM outputs are non-deterministic, context-sensitive, and vulnerable to distribution shift in ways that unit tests cannot capture. Evaluation fills that gap.

A system without an evaluation strategy is a system whose quality is unknown. This is not a defensible position for production software.

---

## When to Use

Evaluation is conducted:
- After implementation and review, before a system is considered production-ready
- When system inputs or upstream data change significantly
- On a scheduled basis for systems with ongoing operation
- When user feedback or monitoring signals suggest degraded behavior

---

## Inputs

- The deployed or near-deployed system
- An evaluation dataset (see construction guidelines below)
- The success criteria defined in the architecture specification

---

## Outputs

- Quantitative results against each success criterion
- Qualitative findings from failure analysis
- A go/no-go determination for production deployment
- Identified areas for improvement (fed into refactor or architecture revision)

---

## Evaluation Dataset Construction

The evaluation dataset is the foundation of the entire evaluation. A poorly constructed dataset produces results that are confident but wrong.

**Independence** — the evaluation dataset must be constructed independently of the model being evaluated. Datasets generated by the same model produce circular validation.

**Representativeness** — the dataset must cover the full expected input distribution, including:
- Typical inputs (the common case)
- Edge cases (inputs at the boundary of the system's intended scope)
- Adversarial inputs (inputs designed to stress failure modes identified in critique)
- Out-of-scope inputs (inputs the system should reject)

**Ground truth** — every evaluation example needs a known-correct answer or a human-validated reference output. Without ground truth, evaluation measures consistency, not correctness.

**Size** — a minimum of 50 examples for initial evaluation. For safety-critical systems or systems with complex output structures, 200+ examples are needed for statistically meaningful results.

## Evaluation Strategies

### Automated Metrics

Use when outputs have measurable properties:

| Metric | Use When |
|--------|----------|
| Exact match | Outputs are categorical or have a definitive correct value |
| F1 / precision / recall | Classification tasks, retrieval relevance |
| BLEU / ROUGE | Text summarization (use with caution — correlates poorly with human judgment) |
| Parse success rate | Structured output reliability |
| Latency (p50, p95, p99) | Latency-sensitive systems |
| Cost per query | Systems with variable token consumption |

### LLM-as-Judge

Use when outputs are too complex for automated metrics but need scalable evaluation.

An LLM judge evaluates generated outputs against defined criteria. This approach scales to open-ended outputs that cannot be matched against a fixed reference.

Design the judge carefully:
- The judge's criteria must be specific and unambiguous. Vague criteria produce inconsistent verdicts.
- Use a different model for judging than for generation where possible. Same-model judging introduces self-preference bias.
- Include both positive and negative examples in the judge's prompt.
- Validate the judge itself against human ratings on a sample before using it at scale.

See [patterns/evaluation_patterns.md](../patterns/evaluation_patterns.md) for implementation patterns.

### Human Evaluation

Use when automated methods are insufficient and the output quality directly affects user trust.

Human evaluation is the gold standard but does not scale. Use it to:
- Validate automated metrics (confirm that high automated scores correspond to high human ratings)
- Evaluate subjective qualities — clarity, tone, appropriateness — that metrics cannot capture
- Establish ground truth for LLM-as-judge calibration

Structure human evaluation tasks carefully. Vague rating instructions produce unreliable inter-rater agreement.

### Retrieval Evaluation (RAG Systems)

Retrieval quality must be evaluated independently of generation quality. A RAG system can have excellent generation on poor retrieval — the LLM compensates with parametric knowledge — masking a retrieval failure that will surface on domain-specific queries.

Evaluate:
- **Retrieval precision**: of the chunks retrieved, what fraction were relevant?
- **Retrieval recall**: of the relevant chunks in the corpus, what fraction were retrieved?
- **Context faithfulness**: does the generated answer reflect only the retrieved context, or does it introduce information not present in the chunks?
- **Answer relevance**: is the generated answer responsive to the actual question?

## Failure Analysis

Quantitative results tell you how often the system fails. Failure analysis tells you why.

For every category of failure identified in evaluation:
1. Examine a sample of failing cases
2. Identify the structural cause — retrieval failure? token budget? prompt ambiguity? routing error?
3. Map the cause to the system component responsible
4. Determine whether the fix is a configuration change, a prompt change, or an architectural change

Failure analysis findings feed directly into the refactor phase. Document them with the same rigor as critique findings.

## Evaluation Anti-Patterns

**Evaluating on training or development data.** The model has seen this data. Performance on it is not predictive of production performance.

**Evaluating only the happy path.** A system that handles 90% of inputs well but catastrophically mishandles the other 10% is not a good system. Evaluation must cover failure modes.

**Reporting a single aggregate metric.** A 90% success rate obscures the distribution of failures. A system that fails 100% of the time on a specific input class — and that class is 10% of production traffic — is a serious problem.

**Skipping retrieval evaluation in RAG systems.** End-to-end evaluation of a RAG system does not reveal whether failures are retrieval failures or generation failures. Evaluate them separately.

**Trusting LLM-as-judge without calibration.** A judge that has not been validated against human ratings may be measuring something other than what you intend.

---

## Connecting Evaluation to the Lifecycle

Evaluation is not a one-time gate. It connects back to every other phase:

- Findings that reveal design flaws return to **architecture**
- Findings that reveal implementation gaps return to **review** or **implementation**
- Findings that reveal prompt or configuration issues are addressed in **refactor**
- Findings that reveal data quality issues return to **exploration**

A system's evaluation results are the most reliable signal of where the lifecycle broke down.
